Fold 3 (`[0.567, 0.85]`, the same fold the fold-dd-blindspot/succession-audit
thread already named) is the one that hard-fails on both — `max_dd` there
exceeds `MAX_DD_HARD_FAIL` (0.40) for the champion *and* for both hand-built
candidates. `constitution.accepts()`'s very first check is `if
fitness(challenger) == -inf: return False` — a candidate whose own
fold-merged drawdown blows the hard gate is rejected before ever being
compared to the champion, before the multiple-testing margin, before the
holdout. Suppressing `consult_moderate`'s exit moved fold 3's max_dd from
-46.8% to -45.8% — real, in the right direction, and utterly insufficient
to clear -40%.

This is a different failure mode than the `vacuous-regression-check`
pattern item 2 has been tracking since 2026-08-22 (where the *champion's*
own -inf dd-corrected fitness makes a downstream comparison check
vacuously pass or fail). Here the *challenger* itself hard-fails on its own
merged stats — the same structural mechanism, but hitting the very first
line of `accepts()` rather than a later comparison. Net effect for this
thread: **exit-role-test's full-history-replay improvement (fitness -inf
→ 0.659) does not survive contact with the fold-merged, dd-corrected metric
the real gate actually scores on.** "Let search decide" cannot decide
anything for either of these two specific gene values — they never reach a
champion-relative comparison at all, let alone the sealed holdout.

## What this changes about the thread

Not itself evidence the underlying idea is wrong — full-history replay and
the 3-fold split can legitimately disagree (fold 3's dominant crash/drawdown
episode is large enough on its own that a ~380bps improvement in one exit
rule's downstream max_dd can't move it under the 40% line). It does mean:

1. A real promotion via this specific gene change is currently blocked by
   the same fold-3 hard-dd-gate structural issue item 2's dd-gate thread
   has been tracking, not by this idea being bad relative to the champion.
2. Any future candidate proposed against v3 right now likely hits the same
   wall unless it moves fold 3's max_dd specifically, which this thread's
   whole exit-mechanism finding barely touches (~1 point of drawdown).
3. The two open threads (exit-mechanism-underperforms and the fold-3
   hard-dd-gate) are more entangled than either looked in isolation — worth
   whoever picks this up next checking whether a MUCH more aggressive
   fold-3-specific fix (not just consult_moderate's exit threshold) is
   needed before this exit idea can ever clear a real gate, or whether the
   dd-gate design question (item 2, still the owner's call) has to move
   first.

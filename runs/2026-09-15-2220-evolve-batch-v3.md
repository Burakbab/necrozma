## New finding: `live_state.json` growth trajectory (see Next-steps item 12)

This cycle's `git push` printed GitHub's large-file warning for the first
time noticed/logged in `AGENTS.md`:

```
remote: warning: File live_state.json is 54.56 MB; this is larger than
GitHub's recommended maximum file size of 50.00 MB
remote: warning: GH001: Large files detected. You may want to try Git LFS.
```

Sampled the file's size at 6 points across recent git history (via
`git cat-file -s <commit>:live_state.json`, since `git log --stat` on this
file is too slow to run interactively — the diffs are enormous):

| date | size |
|---|---|
| 2026-09-11 21:53 | 38.0 MB |
| 2026-09-12 19:33 | 44.0 MB |
| 2026-09-13 19:14 | 49.4 MB |
| 2026-09-15 00:23 | 53.6 MB |
| 2026-09-15 16:18 | 56.0 MB |
| 2026-09-15 22:20 | 57.2 MB |

~4.8 MB/day average growth over the last 4 days. At that rate the file
reaches GitHub's **hard** 100MB per-file push limit around **2026-09-24 to
2026-09-25** — roughly 9 days out, well within this project's operating
horizon.

Root cause, found by breaking down the current file's top-level keys by
serialized size: `researcher_memory` is 29.1 MB of the file's 57.2 MB
(`lineage` is a comparatively small 5.7 MB — it's already capped at 200
entries by `core.live._trim_lineage`, working as designed). Inside
`researcher_memory`, the `tested` field is a list of **17,710** entries,
each the *full* genome patch (`agents/researcher.py`'s `Researcher.key()`
returns `tuple((k, str(v)) for k, v in sorted(m.patch.items()))` — every
gene key/value pair in the mutation, not a hash) — some blind perturbations
touch ~38 genes at once, so individual entries run into the hundreds of
bytes to low KB. This list has **no cap or trim anywhere** (confirmed:
`grep` for trim/cap logic near `tested` in `loop/evolve.py` and
`agents/researcher.py` found nothing) — it only resets when the champion
is beaten, and the champion hasn't changed since the v2→v3 promotion. Since
the champion has now gone unbeaten across every batch this week
(`aggregate_fitness` flat at 1.537), this list grows every single
generation with no bound in sight, which is exactly the growth rate
observed above.

**Not fixed this cycle** — scoped as Next-steps item 12 instead. The
obvious fix direction (store a stable hash of the sorted patch instead of
the patch itself in both the in-memory `Researcher.key()` identity and the
persisted `researcher_memory["tested"]` list) touches a cross-cutting
identity used in at least 7 places in `evotrader_bundle.py`
(serialize/deserialize at multiple CLI command sites) plus
`agents/researcher.py:307` and `loop/evolve.py`'s `EvolutionRun`, and needs
a decision on backward compatibility with the 17,710 full-patch entries
already committed in the live `live_state.json` (migrate them to hashes
once, or let old and new formats co-exist during a transition) — real
design work, not a quick edit, and higher blast radius than this cycle's
remaining time/attention budget should risk given how many other scheduled
sessions read and write this same file. Flagging with the full trail here
so the next session that picks it up doesn't have to re-derive the root
cause.

## A second recurrence of item 9's double-backgrounding anti-pattern, this time on the verification pytest

The `evolve` batch itself was backgrounded correctly (single mechanism:
the harness's own `run_in_background` option directly on the `evolve`
command, no `nohup`/`&`). But the follow-up verification `pytest` run was
launched as `python3 -m pytest -q > log 2>&1 &` (a trailing shell `&`)
*and* passed with the tool's own `run_in_background: true` — exactly the
double-backgrounding pattern item 9 warns against. The tool reported the
wrapper "completed" in a few seconds (having only run the `echo` of the
child PID), while the real `pytest` process (PID 1315) kept running
detached for its full ~145s. Caught immediately by checking the log file's
content against what a completed run should show (cut off at 57%) and
`ps aux`/`kill -0` for the real PID, then waited correctly by polling that
PID until it exited rather than trusting the wrapper's reported exit. No
state was touched by this mistake either way — this is the third logged
recurrence of this exact root cause (pairing the tool's own backgrounding
with a shell-level `&`), after the 2026-09-09 ~01:19 UTC and 2026-11-27
~22:17 UTC instances. Re-confirms item 9's existing wording doesn't fully
prevent this: the lesson is to never type a trailing `&` at all when also
requesting `run_in_background: true`, full stop, regardless of what's
being backgrounded.
